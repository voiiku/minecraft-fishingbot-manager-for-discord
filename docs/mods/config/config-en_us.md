# The config file
[简体中文](config-zh_cn.md) | **English**

* Code: `src/config.rs` (the runtime `Config` and its accessors) and `src/config/{schema,parse,validate,template}.rs`
  (the tables and the file shape of `[paths]`, parsing, validation, the template)
* File: `minecraft-fishingbot-manager-for-discord.conf.toml` next to the executable (the name is fixed by
  `CONFIG_FILE_NAME` and cannot be changed)
* It does not depend on the working directory and reads no environment variables: placing the binary and the config in the same directory is enough, and systemd and similar supervisors need no extra settings.
* The file contains the bot token; `chmod 600` is recommended.

## 1. Load flow (the very beginning of startup)

1. `config::Config::get_or_init()` locates the config file path.
2. When the file does not exist, one is generated from the repository's `minecraft-fishingbot-manager-for-discord.conf.example.toml`: the template is written and the note is printed in this step, then the process exits with code 0 without connecting to Discord. When the file exists, the path found is printed to the terminal before continuing (no logger is installed yet, so the note appears only in the terminal; the `config loaded: ...` line in the program log is written by `ProcessLog::get_or_init`).
3. When the file exists, its text is read. `Config::from_toml_text` parses the TOML into a value tree, recursively trims every string value, and maps the result into the runtime `Config` through Serde's `Deserialize` implementation (the only cleanup in the whole chain). The three keys of `[paths]` are expanded into paths rooted at `base_dir` by `Paths`'s own `Deserialize` implementation. This step handles format parsing and structure conversion only; it does not apply value rules.
4. `validate` first checks `i18n.language`: the error text is fixed English and does not call `text::get()`. Once valid, the language is installed immediately, and the remaining fields are checked for values, ranges and the runtime environment (for example required values, port ranges, and whether the configured directory and JAR exist).
5. When reading, parsing or validation fails, the error reports "config entry + field name + requirement" and exits; the process never runs with an invalid value.
6. On success the config is written into a `OnceLock`: read once at startup and kept in memory. Editing the config file while the process runs has no effect; restart the process for the new config to take effect.

`Config::from_toml_text` removes whitespace around string values: extra spaces, indentation and line breaks in the file never reach the code, so config readers (`main.rs`, the business layer) use the value as-is and do not call `trim()` themselves. To keep surrounding whitespace, write the escape (in TOML, `"\u0020"`).

Deserialization relies on `#[derive(Deserialize)]` on `Config` and its field types. Serde maps TOML table and key names to the corresponding struct fields; a type mismatch, a missing required field or an unknown field returns a parse error. There are **no in-code defaults**: every table and every field must be present, so a missing key or a typo fails at startup instead of silently using a default. Path fields are converted by `Paths`'s own `Deserialize` implementation into runtime paths rooted at `base_dir` (`bots_dir` is derived in code); the remaining value rules are handled by the later `validate` step.

After the config is loaded, the process entry **generates the game-side config** from `[fishingbot]` during startup (FishingBot's `conf.json`, at the path from `paths.fishingbot_config_file_name`): the old file is deleted first, then a new one is written. A failure is handled as a config error (an `ERROR` record and exit code 1). Section 3.2 explains why it is generated and what it contains.

## 2. Public interface

`Config` exposes the following interface; apart from the `config_file_path` field, these are associated functions (the module has no standalone accessor functions; the runtime `Config` is defined in this file). The process entry therefore needs only one line, `let settings = config::Config::get_or_init();`:

* `Config::get_or_init()`: fetch the config; this is the only config entry point used by the process entry. The first call locates, reads, parses and validates the config, then returns the loaded `&'static Config`. When the file is missing and a template is generated, the function prints the note and exits with code 0; when the config is invalid, it reports the error and exits with code 1. Both failure paths end the process inside the function, so the return value is always a usable config and the caller never checks a result.
* `Config::get()`: the loaded `Config`.
* `Config::admins()`: the admin table (short for `Config::get().admins`).
* `Config::install_dir()`: the deployment directory (where the executable is); returns an error message if the path cannot be determined. The config and the program log live there.
* the `config_file_path` field: the config file path used by this run (computed from the executable's location at load time and stored in the struct).

`Config::get()` panics while no config is loaded, with the text from `text::bootstrap::CONFIG_NOT_LOADED` (an internal invariant message; no language is installed yet, so it is fixed English). The first thing the process entry does is `Config::get_or_init()`, so a panic here means the call order is wrong. The config file path is stored as a field of `Config` (computed once at load time); whether a config is loaded is still answered only by the single `OnceLock<Config>`.

## 3. Table structure

The order matches the example config: tables a new deployment usually needs to change come first (credentials, paths and the game-side config `[fishingbot]`), followed by the three tables adjusted for the game server or JAR (keywords, echoes, language), then the runtime parameters, start queue and timing, and finally the raw log, `/ping` defaults, log switch and display text. The example config's explanatory comments are mainly English; the complete Chinese original of `[text].help` is also kept in comments above that setting for Chinese readers. A few lines start with `# CHINESE_SIMPLIFIED:` and state the value to use for a Chinese deployment (only the two `[command_echo]` echoes and `[i18n] language` need them), see [i18n-en_us.md section 1](../i18n/i18n-en_us.md).

* `[discord]`: `token`. The bot token, the only credential and required.
* `[paths]`: `base_dir` (absolute), `jar`, `fishingbot_config_file_name` (relative). The data root, plus the JAR and game-side config file names, resolved relative to it.
* `[fishingbot]`: `server_ip`, `server_port`, `default_protocol`, `auto_reconnect`, `auto_reconnect_time`, `start_text`, `announce_type_console`, `announce_type_chat`. The keys of the game-side config (FishingBot's `conf.json`) that **this project exposes**; that file is generated from them at startup (section 3.2). The whole table is required; the values can be copied from the example config.
* `[admins]`: `"Discord user ID" = "name"`. The admin list; keys must be plain numeric Discord user IDs (snowflakes).
* `[keywords]`: `online`, `filter_regex`. The only log keywords that vary by deployment and must be filled in by hand: the game server's join message, and the regular expression that filters spam lines before they are written (`grep -v -E`). There is deliberately **no** "process finished" keyword: that marker was written by an older wrapper script (`>>> 机器人进程已结束或被手动中止 <<<`), this project does not write it, and whether the process is gone is read from the screen session state (a `(Dead ...)` shell). Section 3.1 explains why only two entries remain.
* `[command_echo]`: `pause_echo`, `unpause_echo`, `wait_ms`, `scan_lines`. These confirm whether `/pause` and `/unpause` actually ran: the first two are the echoes the JAR prints when it receives the command (upstream messages `command-pause-executed` and `command-unpause-executed`; fill in the values for the JAR's language, for example `已暂停钓鱼` / `已恢复钓鱼` for a Chinese JAR). After sending, wait `wait_ms` milliseconds and check the end of the newest log (only the last `scan_lines` lines) for those two sentences.
* `[i18n]`: `language`. The language the program runs in; it affects Discord texts, the program log and error messages. The value is the constant name from FishingBot's own `i18n.Language` and is also written into `conf.json` as `misc.language` (the same value, not mapped), so the two values never need manual alignment. This project implements `ENGLISH` and `CHINESE_SIMPLIFIED`; changing it and restarting is enough, with no rebuild. See section 3.1.
* `[runtime]`: `java_opts`, `screen_prefix`, `token_file`, `bot_logs_dir`, `max_reply_log_lines`, `max_reply_chars`, `max_autocomplete_choices`. The runtime parameters of a single bot. `bot_logs_dir` holds only this project's logs (FishingBot's own raw log sits beside it under `[raw_game_logs] dir_name` as `[raw_game_logs] file_name` and points at `discard_path`, see [utils-en_us.md section 7](../utils/utils-en_us.md#7-the-two-logging-streams)); `max_reply_chars` limits the length of a single reply (Discord's limit is 2000 characters; an overlong message fails to send); `max_autocomplete_choices` limits the autocomplete suggestions for bot-name options (range 1–25, Discord's hard limit).
* `[startup_queue]`: `max_batch_size`, `bot_login_interval_ms`, `batch_login_interval_ms` and `max_pending_requests`. They define, in order, the maximum bots per batch in the global FIFO start queue, the sign-in gap between adjacent bots in a batch (milliseconds), the gap between batches (milliseconds), and the maximum number of waiting requests (excluding the active one). The table and every field are required, and every value must be greater than zero. `bot_login_interval_ms` staggers adjacent bots inside a batch. `batch_login_interval_ms` spaces batches: it counts from the moment the previous batch was popped, and the next batch starts only after at least this long (verification runs in parallel and is not counted as batch-to-batch waiting); this also applies when the previous batch held a single bot, so the first command after a long idle does not wait. Microsoft rate-limits sign-ins per egress IP; see [troubleshooting section 12](../../troubleshooting/troubleshooting-en_us.md) for the values. `/start`, `/startall`, `/restart` and `/restartall` share this queue; `/bot login` does not use it. At most `max_pending_requests` bots wait in the queue; the rest are returned to the caller immediately (the reply states this), and pending entries are dropped when the process restarts. The result timeout is not configurable: it is derived from this table and `timing.check_grace_ms` (`StartupQueue::result_timeout`; the grace period is counted once): `2 * (ceil(max_pending_requests / max_batch_size) * max(batch_login_interval_ms, (max_batch_size - 1) * bot_login_interval_ms) + check_grace_ms)`. When it expires, bots without a result are reported as "unconfirmed" in the reply (and one line is written to the program log). A slower per-bot stagger or a larger queue extends it automatically.
* `[timing]`: `check_grace_ms`, `stop_grace_ms`, `stop_settle_ms` and `watchdog_window_ms`. These per-flow waits are in milliseconds. `check_grace_ms` is the session-survival grace period after every bot in a start request has been launched (the check runs twice: immediately after launch, then after the grace period; one wait per start request, not per bot). `stop_grace_ms` is how long to wait for the JVM to exit gracefully after the stop signal, before force-killing it; `stop_settle_ms` is the settling wait after a force kill and before the session state is checked again. `stop_grace_ms` and `stop_settle_ms` are only read and have no value validation. `watchdog_window_ms` is the gateway watchdog's judging window, also used as the wait before rebuilding the connection; the REST probe interval (a third of the window) and the first-handshake timeout (twice the window) are derived from it instead of being separate keys, see [watchdog-en_us.md](../watchdog/watchdog-en_us.md).
* `[raw_game_logs]`: `dir_name`, `file_name`, `discard_path`. The convention for FishingBot.jar's own raw log (directory name, file name, and where the contents are discarded). It follows the JAR and the whole table is required; the example config uses `raw`, `log0.log` and `/dev/null`.
* `[ping]`: `default_ping_host`, `default_ping_port`, `timeout_ms`. The default target and timeout of `/ping` when it is called without arguments.
* `[log]`: `debug`. The program log level switch. With `false`, this project's records start at `INFO` and third-party crates (serenity, poise) at `WARN`; with `true`, both go down to `DEBUG` (fully open; finer `TRACE` records are still not captured). This is the only level switch (environment variables are no longer read); details in [process-log-en_us.md](../process-log/process-log-en_us.md).
* `[text]`: `help`. The full output of `/help` (a multi-line string, so the wording can be changed without a rebuild).

### 3.1 Where the keywords live: `[keywords]`, `[command_echo]` and `[i18n]`

* Strings that vary by deployment and can only be supplied by the deployer go into `[keywords]`: the game server's join message (`online`) and the spam noise to filter on this server (`filter_regex`).
* The `/pause` and `/unpause` echoes go into `[command_echo]` (`pause_echo`, `unpause_echo`): the JAR prints them, but they only exist in a build containing those two commands (the upstream build has neither). Putting them in the config allows a different build to be configured in place without a rebuild.
* The reconnect message's prefix and suffix stay in the program (`src/text/*.rs`, the `jar_*` methods) and follow `[i18n] language`: they change only with the JAR's language and are the same for every deployment, so copying them into the config would add another failure point. That language is also written into `conf.json` as `misc.language` (section 3.2), so the JAR always uses the same language. Manual alignment was once required; now the two values cannot disagree.
* "Process finished" needs no keyword: an older wrapper script wrote an end marker into the log with `java ... | tee bot.log; echo marker >> bot.log`, while this project starts the session itself and does not write it. The check therefore reads the screen session state instead (a `(Dead ...)` shell, see [utils-en_us.md](../utils/utils-en_us.md)), which is more reliable than copying a marker: it does not depend on the JAR version, the script or the language.

The criterion is "who decides this string, and does it have to change with the build": what the deployment environment decides goes into `[keywords]`, what the JAR build decides goes into `[command_echo]`, what the JAR's language decides follows `[i18n]`; a judgement that is not about a string (is the process gone) reads the session state directly.

### 3.2 The game-side config (`conf.json`) is a generated file

FishingBot only reads JSON (`-config <path>`) and has **no command-line argument that overrides an individual setting** (its startup arguments are only `-nogui`, `-help`, `-logsdir`, `-config`, `-refreshToken` and `-onlyCreateConfig`). Therefore, merging `conf.json` into the TOML can only be **one-way generation**: the TOML is the single source of truth, and the JSON is written when the process starts (the code is in `utils/fishingbot_config.rs`).

Generation method: **use the template shipped with the repository as the base and override only the corresponding keys in `[fishingbot]`.**

* The template is the repository's `fishingbot-config.example.json`, a **complete** FishingBot config (taken from the default file upstream generates, with defaults adjusted for this project: console and chat announcements off, `/home fishing` as the default cast command, a longer `auto-reconnect-time`, and so on). It is compiled into the binary with `include_str!`, so no extra file is needed at deployment.
* The overridden keys are the managed list in `utils/fishingbot_config.rs` (ten dotted paths), one to one with the fields of `[fishingbot]`; `misc.language` is written directly from `[i18n] language` (whose value is the JAR's constant name, see `text::Language::from_name` / `name`), so there is no manual entry and the two values need no alignment.
* Every other key is left as the template has it, so the output is **always a complete config** and never relies on the JAR to fill in missing fields. (Measured on v2.13.15: it does fill in missing fields and writes the file back, but the JAR decides what is added, and every process start leaves one more `Your configuration was incomplete. The missing fields were added!` line in the bot log.)
* **The old file is deleted first**: it is a generated file, so hand edits do not survive the next start. Change `[fishingbot]` instead, or change the template to change a default.

When upstream changes the config structure (adds, renames or removes a key): take a default `conf.json` generated by the new JAR, copy it over the template and run `cargo test`. `template_holds_every_managed_path` fails first (a managed path is missing from the template); follow its message to sync `managed_values` and `[fishingbot]`. This is the **only** maintenance point that must follow upstream.

`[fishingbot]` is the single entry point for the desired game-side config; the `conf.json` on disk is what FishingBot actually reads (and what `/show botconfig` sends). Note also: changing `[i18n] language` changes the JAR's language, and the two `[command_echo]` echoes (`pause_echo`, `unpause_echo`) are printed by the JAR, so they must be changed to the matching language as well.

## 4. Field rules

* Every field is required: there are no in-code defaults, so omitting one or misspelling it (caught by `deny_unknown_fields`) fails at startup. The example config has every key filled in and can be used as the starting point.
* Path rules (`paths`): `base_dir` must be absolute; `jar` and `fishingbot_config_file_name` must be relative and are resolved against `base_dir`; `bots_dir` is derived in code as `base_dir/bots` and is not written in the config. A relative `base_dir` or an absolute `jar` fails at startup.
* `[discord]`: `token` is the only credential; an empty token can never connect (startup fails). There are no other fields, and slash commands are always registered globally (Discord can take up to an hour to propagate them).
* `[admins]` may be empty (then there are no admins and everyone manages their own bots), but a key must be a plain numeric Discord user ID and a name cannot be blank. A mistake in either silently breaks permissions, so it is rejected at startup. Use `/whoami` to get your own user ID.
* `[i18n]`: `language` must be a supported value, namely a constant name from FishingBot's own `i18n.Language` (this project implements `ENGLISH` and `CHINESE_SIMPLIFIED`; upstream values such as `CHINESE_TRADITIONAL` and `FRENCH` are rejected because this project does not provide those texts). The valid values are defined in one place, `text::Language`, and the error lists them all. The value must match exactly (case sensitive, like the JAR's enum names; surrounding whitespace is ignored). The example config uses `ENGLISH` (change it to `CHINESE_SIMPLIFIED` for a Chinese JAR deployment); both languages are compiled into the binary, so changing the line and restarting is enough.
* `[log] debug` decides whether framework logs are collected too. With `false`, this project's records start at `INFO` and third-party crates (serenity, poise) at `WARN`, because they print `INFO` on every heartbeat and would drown the important lines (startup, commands, replies); with `true`, both go down to `DEBUG` (fully open; finer `TRACE` records are still not captured).
* `[fishingbot]`: the whole table is required (the values can be copied from the example config), and invalid values are reported at startup with the field named. A wrong value otherwise only makes the JAR **run quietly with its defaults** (measured: an unknown enum value falls back silently, and an unrecognised version is probed by the JAR itself), so rejecting it at startup is clearer. Rejected values: an empty `server_ip`, a zero `server_port`, a `default_protocol` that is neither `AUTOMATIC` nor version-shaped (`1.20`, `1.20.4`), an empty string inside `start_text`, and either `announce_type_*` outside upstream's five values (`ALL`, `ALL_BUT_FISH`, `ONLY_ENCHANTED`, `ONLY_BOOKS`, `NONE`). Online mode, offline usernames, automatic cast rules, realms and GUI entries are **not exposed**: they use the template's values (this project runs in online mode, and every account logs in through Microsoft).
* `[command_echo]`: `wait_ms` is how long to wait after sending a command before checking the log (too short and the echo is not there yet); `scan_lines` is how many trailing lines to check (a larger number tolerates more noise: the echo can be pushed out of the trailing range by a few unrelated lines, at the cost of reading more lines). Both must be greater than 0: waiting 0 means checking immediately after sending, before the echo can reach the log.

## 5. Validation (`validate`)

Validation is split by table: each TOML table has a `validate_<table>` function, and `validate()` contains only those calls, in startup order; `[log]` has only the boolean `debug` switch and no validator.

Language is the first check: `validate()` calls `validate_i18n` first. It only parses `i18n.language`, its error text is fixed English, and it does not call `text::get()`. Once the language is valid it is installed immediately, and the per-table `validate_<table>` functions then use the configured language.

It covers the following three basic categories of problem (see the module docs of `validate.rs`):

* Required entries must not be empty: `ping.default_ping_host`, `discord.token`, `keywords.*`, `command_echo.pause_echo`, `command_echo.unpause_echo`, `text.help`, `runtime.screen_prefix`, `runtime.token_file`, `runtime.bot_logs_dir` (the last three must also contain no spaces or slashes and must not be `.` or `..`), `raw_game_logs.discard_path`, and `raw_game_logs.dir_name` / `raw_game_logs.file_name` (these two must be plain names as well).
* Numeric ranges: `ping.default_ping_port` must not be 0; `runtime.max_autocomplete_choices` must be between 1 and 25 (Discord's hard limit on suggestions); `startup_queue.max_batch_size`, `startup_queue.bot_login_interval_ms`, `startup_queue.batch_login_interval_ms`, `startup_queue.max_pending_requests`, `ping.timeout_ms`, `runtime.max_reply_log_lines`, `runtime.max_reply_chars`, `timing.watchdog_window_ms`, `timing.check_grace_ms`, `command_echo.wait_ms` and `command_echo.scan_lines` must be greater than 0 (a watchdog window of 0 degrades the decision and can never prove "still connected"; the probe interval and the first-handshake timeout are derived from that window, so the "probe must not be slower than the window" rule no longer exists).
* Strings that get spliced into a command or path: `runtime.java_opts` forbids `'`, `"`, backtick, `$`, `;`, `&`, `|`, `<`, `>` and newlines (it is inlined unquoted); `keywords.filter_regex` must not contain a single quote (it is inlined into `grep -v -E '...'`); `paths.jar` and `paths.fishingbot_config_file_name` must not contain one either.

In addition, the two `command_echo` echoes must differ, and neither may contain the other (complete equality included): otherwise the log line cannot be attributed to a command and the decision always favors whichever is checked first.

Two more checks belong to "is the environment ready" and also fail at startup: `paths.base_dir` must be a directory and `paths.jar` must be a file. If either is wrong, the failure only appears when a session is launched, with a much less clear message.

Everything else is out of scope: timing values, address selection and whether a name may contain Chinese characters are left to the user's judgement. `[discord]` has one rule (the token must not be empty); `[log]`'s `debug` is a boolean switch with no rule; `[timing]` has two (`check_grace_ms` greater than 0 and the gateway window greater than 0); `[command_echo]` has two (both echoes non-empty and neither containing the other, and both duration values greater than 0).

## 6. The template (`template`)

* The template is the repository root's `minecraft-fishingbot-manager-for-discord.conf.example.toml`, compiled into the binary with `include_str!`, so a release does not need to carry an extra file.
* The generated template is identical to the example file. A unit test checks every table and field in the example (a missing field would make a user who copies the template fail to start) and checks that every key is documented here.

## 7. Why the config is split into tables (instead of one flat struct)

In code there is one `Config` plus one struct per TOML table (`Config::ping`, `runtime`, `timing`, ...). This is not an extra layer; it keeps the name identical in three places:

* the key in the config file: `bot_logs_dir` under `[runtime]`;
* the way the code reads it: `config::Config::get().runtime.bot_logs_dir`;
* a startup validation error: `配置项 runtime.bot_logs_dir 不能为空`.

Flattening the structs into one large struct of concrete fields requires deciding what happens to the TOML tables; none of the three options is worthwhile:

* Flatten the file as well (`runtime_logs_dir = "logs"`): the file still matches the struct one to one, but every existing deployment must rewrite its config (this project runs with `deny_unknown_fields`, so the old form fails to start), and `[admins]` (user ID to name) is a map, so it cannot be flattened into "one concrete setting each". Field names would also clash (`log.debug` and `runtime.debug`, for example) and need prefixes, after which file keys and field names no longer match and validation errors cannot reuse the names from the file.
* Keep the file split and flatten the structs: serde cannot do this in that direction. `#[serde(flatten)]` means "spread a struct into the file"; spreading `[runtime]` into a flat struct would require a hand-written path-based lookup layer, which adds code rather than reducing it, and field-level errors would degrade into hand-written strings that drift away from the file.
* Generate a "flat view" with a macro: this keeps both the file and the structs, but the per-field doc comments become macro arguments and `cargo doc` no longer shows the current explanations, which is a poor trade-off for a project where the config is the documentation.

The conclusion is to keep the tables: the dotted layer after `config::Config::get()` is an acceptable cost, and it provides exactly "file key name equals struct path equals validation error". "Read once at startup, then read fields directly" also holds: `Config::get_or_init()` writes the config into a `OnceLock` at the very beginning, and every later `config::Config::get()` is a memory read with no I/O.
